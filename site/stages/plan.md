# 03 plan

<StageHeader stage="plan" />

plan 把通过审批的方案按阶段拆成一份可以逐条勾选的任务清单。但它真正的作用是：**在开工前冻结所有验收门限**。门限一旦冻结，后续阶段只能拿结果去对照它，不能回头修改。

## plan.md 的五节

`03-plan/plan.md` 必须有五节：**问题、方案、任务、验收门限（冻结）、范围外**。

- **任务**按阶段分组，写成可勾选的清单（`- [ ]`），每条写清要交付的产物，以及由哪个验证门判定。
- **验收门限**带编号（S 仿真、M 建模、R 参考图、V 渲染）、数值和来源（沿用历史标准，或为了某个风险新加），并写明「冻结于 YYYY-MM-DD」。
- **范围外**和需求记录的「不做什么」一致。
- **不写时间预估。** 验证门会查「预计 / 预估 / 上限 + 时长」这类字样。

门限同时写进机器可读的 `03-plan/thresholds.json`，后面所有验证门都只读这个文件。

## 门限从哪来：每条风险都要有人盯

方案页的风险表里，每一条风险至少要对应一条门限或一个负例。例如薄切片 01 的风险 R3「隔板间距约 120 mm，水平伸入时可能碰到上一层；搬运时盖子可能滑动」对应 S4（禁止接触对）、S5 和 S6（盖子位移上限）；风险 R5「支撑后释放误判」对应 S7（松爪前的支撑力）和负例 N1（去掉托面）。

## 负例：证明门限真能抓到错

只看到 PASS 还不够。测量代码写错了，或者门限定得太松，任何情况都会判 PASS。所以每条关键门限都要配一个**负例**：故意把一件事做错，门限必须判 FAIL。负例单独列表，写明期望 FAIL 的门限，并写进 `thresholds.json` 的 `simulation.negatives`（编号、说明、变体名、期望 FAIL 的门限）。仿真验证门会把每个负例跑一遍，**没判 FAIL 的负例会让整道门 FAIL**。

## 危险探针：先确认这个「错」真的危险 {#hazard-probe}

负例针对的危险可能根本不存在。两个项目各踩过一次：

- **N3 v1（薄切片 01）**：把盖的摩擦设为零，期望搬运中盖滑落。结果没触发。用独立模型扫参数才弄清楚：盖裙在水平方向把盖锁死了，板倾斜 60°、搬运快 5 倍、2 N 侧向冲击下，盖的位移都小于 0.6 mm。危险本身不存在。v2 改成「夹取高度偏高 11 mm」：指垫夹到盖裙，盖被提走、板留在原处，S5 = 1.2 m，按预期触发。
- **N6 v1（全流程实验室）**：分液目标偏移 10 mm。拖动下面的滑块看看为什么它判不出错：

<HazardProbe />

所以现在的规则是：**设计负例之前，先做一次危险探针**，用独立的小模型扫一下相关参数（倾角、速度、冲击力、错位量），确认在操作范围内这个危险真的会发生、门限也真的能抓到，再写进 plan。负例失效时，**改负例，不改门限**，并在 `thresholds.json` 的 `revisions` 里写明原因。

## 验证门查什么

```bash
uv run wb gate <项目> plan
```

- `plan.md` 存在，五节齐全且不为空；
- 任务是可勾选清单；
- 门限写明冻结日期；
- 门限有编号行；
- 不含时间预估。

## 两条容易混的规则

- **runner 的停止条件不是验收门限。** 仿真脚本里「超过多少就提前停」的界限，和最终验收门限要分开命名。旧项目里一次运行「完成」了 117.7 s，但最大被动平移 0.225 mm 超过 0.1 mm 的严格限，仍然是 FAIL。
- **测量代码要对照门限原文写。** 薄切片 01 的 S8 目标点是「抽屉收回后的托槽」，S11 只统计「任务物体」。代码写错了就改代码，不改门限。
