# 一页看懂整个流程

**场景流程**（pipeline）把一个实验室或工作站的需求，一路做成可仿真、可渲染的三维场景：动作由 MuJoCo 物理引擎算出来，再由 Blender 照着仿真结果渲染成片。它由一串固定的**阶段**组成，每个阶段都用一条命令判定做完没有。这一页讲清楚四件事：为什么要这样做，七个阶段各管什么，数据怎样从头流到尾，以及每个阶段内部固定要做的几件事。

::: tip 读完这一页你应该能回答
- 为什么动作必须先在物理引擎里跑出来，而不是在 Blender 里直接做动画？
- 七个阶段各自回答什么问题、交给下一个阶段什么？
- 「这个阶段做完了」由谁、按什么判定？
- 你在整个过程里需要出场几次？
:::

## 为什么要有一条固定的流程

在这条流程之前，团队试过两种做法，都失败了：

- **在 Blender 里直接做动画。** 美术给板、盖、管设定每一帧的位置，画面可以很好看，但手没夹紧、板穿进台面、盖早该滑落，画面上都看不出来。这条路因为穿模和夹爪错误被否决（[ADR-0003](https://github.com/CaiZongyuan/world-building/blob/main/docs/adr/0003-physics-first-then-pose-bind-render.md)）。
- **一个大而全的建模 skill，从参考板一路做到交付。** 仿真极慢、问题频发，而且**看不出是哪个阶段出的问题**。一个历史场景宣称 PASS，却无法从归档复现。

于是这条流程定了三条原则：

1. **先物理，后渲染。** 动作一律由 MuJoCo 仿真产生，渲染只照抄仿真记录的位姿，不加一帧手调。
2. **每个阶段都要过门。** 验收门限在开工前冻结，阶段结束时由脚本对照判定。判 FAIL 就改设计，不改门限。
3. **人只在必要处出场。** 你决定方向（做什么、做到多真、看起来像什么）；工程细节由 agent 查证后自己决定，写清理由和证据。

流程本身也是这样「长」出来的：先用只有一个工艺步骤的**薄切片**走完全部阶段，逐阶段记下卡点和真实成本，再提炼成 skill `lab-scene-pipeline`（[ADR-0001](https://github.com/CaiZongyuan/world-building/blob/main/docs/adr/0001-grow-new-skill-from-vertical-slice.md)）。然后用这个 skill 做了 14 步的全流程实验室。

三处容易误解的地方：

- **方案预览不只是「出个方案」。** 它要用方盒代理把整个场景在运动学上摆一遍（运动学预演），用事实核查需求。薄切片 01 仿真阶段的 14 次返工里，有 9 次只要摆出位姿就能发现。
- **plan 的核心不是任务清单，而是冻结门限。** 「做成了」的标准在这里写成带编号的数字，后面所有验证门都只读 `thresholds.json`。
- **参考图只冻结外观风格。** 尺寸来自尺寸表，每一项都要标明来源；参考图和设计不一致的地方逐张注明，不追求重新生成。

## 数据怎么从头流到尾

每个阶段的产物就是下一个阶段的输入。把这条线记住，就知道任何一个文件是从哪来、给谁用的。

| 产物 | 谁生产 | 谁读它 | 为什么重要 |
|---|---|---|---|
| `requirements.md` | 需求访谈 | 方案预览、plan | 六节：目标、不做什么、工艺步骤、设备、保真度、算力预算。工艺步骤表直接成为方案页时间线的数据源 |
| `preflight.json` / 预演报告 | 方案预览 | 方案页「工程决策」、仿真 | 布局和取放位姿在这里定；全流程实验室的预演路线被仿真阶段直接沿用 |
| `thresholds.json` | plan | **之后所有验证门** | 冻结的门限和负例。只能对照，不能放宽 |
| `dimensions.md`、`load_path.svg` | 参考图 | 建模 | 尺寸以它为准，每项标明「标准锚点 / 设计假设 / 实测」 |
| `design.py` → `design.json` | 建模 | Blender 构建、MJCF 构建 | 唯一的参数源，视觉和物理两份模型都从它生成 |
| MJCF、GLB、`mapping.json` | 建模 | 仿真、渲染 | 物理模型给仿真；视觉模型和映射表给渲染 |
| `results/*.json` | 仿真 | 仿真验证门 | 名义流程和每个负例的测量值 |
| `states_30fps.npz` | 仿真 | 渲染 | 每个刚体每一帧的位姿。渲染只照抄它 |
| `film.mp4`、关键帧 | 渲染 | 你 | 不加速、不剪辑，帧数等于仿真时长 × 30 |
| `stage-log.md`、`gates/*.json` | 每个阶段 | 你、复盘、继续推进 | 每一步的实测数据和判定证据 |

## 一个阶段内部的固定动作

不管哪个阶段，都要满足同样的五步才算完成：

1. **阶段说明。** 用几句话告诉你：这一阶段的输入、要做什么、用什么工具、怎么算完成、最可能出什么问题。
2. **做出产物**，放在 `<项目>/<阶段目录>/` 下。
3. **跑验证门**：`uv run --extra sim wb gate <项目> <阶段>`。判 FAIL 就先复盘，调整做法后再跑；只有完全卡死才停下来报告。门限不放宽，失败记录全部保留。
4. **写阶段日志和经验记录**：在 `stage-log.md` 里填这一阶段的一行和卡点小节，并更新仓库 `docs/lessons/` 里对应的文件。
5. **同步**：用 `hf upload` 上传项目目录；改了流程代码或文档，就提交并推送 git。

验证门怎样判定、五种结果分别意味着什么，在[核心概念](./concepts)里可以亲手试一次。

## 流程和项目分别放在哪

- **GitHub 仓库 `world-building`** 只放流程本身：skill、经验记录、术语表、ADR、`wb` 命令行、方案预览模板，以及每个项目的方案预览页（`proposals/`，方便直接浏览）。
- **HuggingFace 数据集 `RickC1999/world-building-projects`** 放每个项目的全部产物：模型、仿真结果、渲染、阶段日志。本地镜像在 `D:\Projects\Robots\projects\`，WSL 下是 `/mnt/d/Projects/Robots/projects/`。
