# 03 plan

## 这一步做什么

把通过审批的方案预览，按阶段拆成一份可以逐条勾选的任务清单，并**在开工前冻结所有验收门限**。门限一旦冻结，后续阶段只能拿结果去对照它，不能再回头修改。

## 输入 / 产物 / 完成判据

- 输入：需求记录、方案预览（含风险表）、历史验收数据（P3 的门限和负例）。
- 产物：`03-plan/plan.md`，包含问题、方案、任务、验收门限（冻结）、范围外五节。
- 完成判据：`wb gate <项目> plan` 判 PASS。plan 与参考图一起在审批点②审核。

## 标准做法

1. 任务按阶段分组，每条任务写清楚要交付的产物，以及由哪个验证门来判定。
2. 每条门限都要有编号（S/M/R/V/N 开头）、数值和来源（沿用历史标准，或是为了某个风险新加）。
3. 方案预览里的每条风险至少要对应一条门限或一个负例（例如 R3 → S4–S6，R5 → S7、N1）。
4. 负例单独列成一张表，写明"必须判 FAIL"的期望结果。
5. 不写时间预估。验证门会检查"预计 / 预估 / 上限 + 时长"这类字样。

## 踩过的坑

- **负例针对的危险可能根本不存在。** 薄切片 01 的 N3（盖零摩擦）就是这样：盖裙把盖锁死了，摩擦为零也滑不动。设计负例之前，先做一次**危险探针**：用独立的小模型扫一下相关参数（倾角、速度、冲击力、错位量），确认在操作范围内这个危险真的会发生、门限也真的能抓到，再写进 plan。
- 负例清单写进 `thresholds.json` 的 `simulation.negatives`（编号、说明、变体名、期望 FAIL 的门限，可选的附加指标条件），验证门从这里读取。

- 不要把 runner 的停止条件和最终验收门限混为一谈（先验经验第 6 条），两者要分开命名。
