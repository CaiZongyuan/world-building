## 根因：可行性问题发现得太晚

仿真阶段的 14 次返工里，有 9 次本可以在**动手建模之前**用很便宜的方法发现。它们都属于**运动学可行性**问题，不涉及动力学：

- 夹爪行程比工件尺寸小
- TCP 的伸入深度与原装指尖、观察站抽屉前面板之间的空档
- 外门开合时扫到机器人底座
- 放板位置够不着；放板时手爪需要"伸过去再回头"
- 内玻璃门开启后横在机器人一侧
- 子体继承了 frame 的旋转，导致板长边方向错误

方案预览阶段只用 IK 查了**点位**能否到达，没有查**工具几何、进出方向、设备扫掠范围**。

## 流程改进：新增"运动学预演"

在方案预览阶段（审批点①之前）加入**运动学预演**：

1. 所有设备、工件、夹具都用**方盒代理**表示，尺寸取自规格书或复用资产。
2. 用多初值、带碰撞检查的 IK 求出**取、放两个关键位姿**，进出方向和夹爪张合轴都要明确写出来。
3. 沿参考轨迹做两种运动学扫掠：机器人对环境；门、抽屉等设备的扫掠范围对静态环境。
4. 预演的结果直接决定布局、夹具形式和取放策略，写进方案预览的"工程决策"一节。

预计效果：建模阶段的设计返工、仿真阶段几何和布局类的返工，大部分会前移到预演中，在约 10 秒一次的迭代里解决。剩下留给动力学阶段的，主要是控制和接触数值问题。

## 其他固定下来的做法

- **只有两个审批点**（方案预览、参考图 + plan）。之后由 agent 自主推进，工程细节也由 agent 决定。这次实践下来是可行的：审批点②之后没有出现必须由用户拍板的问题。
- **门限冻结在 `03-plan/thresholds.json`**，验证门只读这个文件。测量代码出了 bug 就改代码，不改门限（这次 S8、S11 各改过一次）。
- **负例要先确认危险在物理上确实可能发生。** 这次 N3 就失效了。
- **Blender 脚本要放在 Windows 盘上。** Windows 版 Blender 读不到 WSL 的 `/tmp`。
- **渲染默认用 draft 档位**：审阅用的成片 720p、16 spp 加降噪就够了，每帧约 0.55 s；1080p、128 spp 要每帧约 13.5 s，只在用户要展示片时才用。开渲前先用 3–6 帧确认曝光和机位。

## 遗留问题

- N3 需要重新设计成能真正触发的负例（#7 仍然打开）。
- 偏置宽指、观察站开槽、布局调整都只在仿真中验证过，没有做强度、制造或真实硬件方面的验证。
- 机器人底座仍然是理想化处理（接触面积为 0，固定在世界坐标）。
