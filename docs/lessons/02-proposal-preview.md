# 02 方案预览

## 这一步做什么

产出一页本地 HTML，让工程师在开工前把方案看透：要哪些设备、场景怎么摆、工艺怎么走、难在哪里。更重要的是，这一步要**用事实核查需求**，把需求访谈里没查过的物理约束暴露出来，交给审批点①决定。

## 输入 / 产物 / 完成判据

- 输入：需求记录、复用资产清单、复用资产的 MJCF 和渲染图。
- 产物：`02-proposal/index.html`、`img/`（效果图、缩略图）、`analysis/`（可达性等初筛脚本及结果）。
- 完成判据：`wb gate <项目> proposal` 判 PASS，用户在审批点①确认。

## 工具与调用方式

- **结构**：8 个固定小节，`id` 依次为 goal / renders / layout / devices / steps / stages / risks / references。设备、工艺步骤、外部参考三张表的数据放在 `<script type="application/json" id="proposal-data">` 里，由 JS 渲染成表格；验证门直接解析这段 JSON。
- **效果图**：imagegen，3 张后台并行，共约 40 s。提示词里只写通用描述（"white seven-axis collaborative robot arm"），不写品牌名，不出现文字和 logo。
- **布局图**：手写 SVG，用一条线性公式把场景坐标映射到像素坐标，并把公式写在注释里。
- **可达性初筛**：MuJoCo `MjSpec` 加载 Menagerie Panda，加一个 TCP site，对关键位姿做阻尼最小二乘 IK，每个位姿试 12 个随机初值。约 30 行代码，几秒跑完。
- **截图自查**：Windows 上的 Chrome 以 headless 模式截全页，分段查看。

## 标准做法

1. 先查清会改变方案的物理事实，再写页面：夹爪行程和工件尺寸、臂展和取放位姿、真实设备尺寸。
2. 工程细节（尺寸、夹爪、层位、可达性）由 agent 自己决定，写在页面最上方的"工程决策"框里，每项附原因和证据，**不要交给用户确认**。审批点只问范围、目标、风格这类方向性问题。
3. 设备状态如实标注：只编译通过不能写成 PASS；理想化的部件就标 IDEALIZED。
4. 外部参考只引用文字和数据，不嵌入外部图片；每条都标明许可，以及是"仅参考"还是"可作资产"。
5. 效果图要标明是"概念图，不是工程图"。

## 踩过的坑

- **把工程细节当成审批事项。** 第一版把夹爪、层位、外形尺寸列成"请用户确认"，用户的反馈是"具体的尺寸问题需要 agent 自己解决，不要麻烦用户"。
- **写时间预估。** 第一版给每个阶段都写了时间上限，用户要求只按阶段、步骤、难度组织；阶段日志只记实测数据。
- **夹爪行程与工件尺寸不匹配。** Panda 原装夹爪行程 80 mm，六孔板宽 85.5 mm，原装手指根本夹不住。需求访谈时我推荐了"先用原装手指"，这个推荐是错的。以后凡是涉及抓取，需求访谈阶段就要先核对夹爪行程和工件尺寸。
- **"沿用旧布局"不等于"沿用旧布局下可达的那个位姿"。** P3 取的是最上层、靠门的板，换成中层或靠里的板就够不到了。
- **验证门正则误报。** JS 模板里的 `<img src="${...}">` 被当成了图片路径，判了一次 FAIL。占位符要跳过；JSON 里的缩略图路径单独检查是否存在。

## 阶段日志摘要

墙钟约 0.2 h 就到了提交审批这一步，验证门失败 1 次，无返工。夹爪和取板层位这两个事实已由 agent 决定。审批点①通过时，用户要求删掉时间预估，并把方案预览 HTML 放进 GitHub 仓库。
