# 01 需求访谈

## 这一步做什么

把用户对场景的想法收敛成一份没有隐含假设的需求记录。这一步只问会**改变方案**的决定（范围、执行者、保真度、预算、审批）。实现细节不在这里问，留给 plan。

## 输入 / 产物 / 完成判据

- 输入：用户的一句话需求；已有资产清单（复用资产的状态与缺口）；可对照的历史数据。
- 产物：`01-requirements/requirements.md`，必含六节：目标、不做什么、工艺步骤、设备、保真度、算力预算。
- 完成判据：`wb gate <项目> requirements` 判 PASS；阶段日志已填。

## 工具与调用方式

- grilling skill：分轮提问，每轮只问当前就能回答的问题，每问附推荐答案。
- 回答之前，事实要先由子代理查清（资产状态、硬件、可复现性）。不要让用户回答 agent 自己能查到的东西。

## 标准做法

0. **需求访谈要交出三张清单，并让用户确认：场景（区域和设备）、流程（每一步在哪里、谁来做、搬什么）、资产（每样东西的来源和实查现状）。** 范围大的项目要做一页范围预览 HTML（`01-requirements/preview/`），把三张清单配上图摊开给用户看，再写需求记录。原则性问题（范围、保真度、执行者）问完，并不等于用户已经知道"具体要做哪些东西"。
1. 先查事实：复用资产能不能编译、历史场景能不能复现、有什么硬件。
2. 一轮问完当前所有可问的问题。每问都给推荐，让"是"等于接受推荐。
3. 用工艺步骤表写需求：每一步标明执行者、难度等级、保真度。这张表会直接成为方案预览时间线的数据源。
4. "不做什么"一节要写得和"目标"一样具体。
5. 用户改写了推荐答案时，记下改写对后续阶段的影响（例：不加速成片 → 渲染帧数 ×4–8）。

## 踩过的坑

- **只问原则、没摊开清单就开工**（全流程项目）。用户问："你不是应该先和我确认完整场景、流程、资产都应该包括哪些吗"。补做的范围预览页里，实查推翻了两项设想：没有现成的机器人导轨；移液工作站可以兼当洁净区。资产现状要**实查**（能不能编译、缺不缺文件），不能只读资产自带的说明文档。

- 只要把门交给执行器而不是机械臂，就去掉了一整类 L3 接触难点。**执行者是需求，不是实现细节**，必须在这里问。
- 历史场景（P3 v3）声称 PASS，但无法从归档复现。需求里只能把它当数据对照，不能写成"复用 P3 场景"。

## 阶段日志摘要

约 0.5 h、1 轮 6 问、无返工。用户改写了 2 问，都是流程偏好：不加速成片、审批点减为 2 个。
